# arcwell — engineer brief (gargantuan)

## 1. Mission

Goal of this project is DMA from NVME to GPU VRAM of Intel Arc A770 and Intel Arc B60 for efficient LLM weight streaming. No host RAM Buffer - except for housekeeping of necessary metadata - is allowed

Build arcwell: a kernel module that streams mixture-of-experts weight files from NVMe into Arc GPU VRAM by controller DMA — no host bounce buffer, no page cache, no per-read filesystem walk. First user: arcint (the host-to-device slot upload path in backend_ov.cpp). You are the Engineer seat. You build and commit on dev; you never push to master; you close every session with a cycle account.

## 2. Hardware and compute reality (know the lab)
- Target cards: an Arc Pro B60 (22.71 GiB usable) and an Arc A770 (15.1 GiB), in the target inference box.
- Compute reality (recorded): SYCL is dead under the xe driver (memcpy abort). Vulkan runs but is slow on Battlemage. OpenCL via OpenVINO is the only measurably fast compute path on both cards.
- Consequence: design the VRAM consumption on OpenCL/OpenVINO. Fence the copy completion against an OpenCL/OpenVINO event, not Level Zero. If you cannot verify the consumption path, do not stream into VRAM.

## 4. Architecture (kernel module)
- arcwell is a kernel module project: the NVMe controller DMAs expert weights
  straight into Arc VRAM, with no other subsystem in the loop. The delivery path
  is the module's ioctl surface (`stub/include/aw_uapi.h`): register a VRAM
  buffer as an NVMe DMA target, then issue storage->VRAM DMA over a block range.
- No userspace data path is part of the architecture. A userspace read lands
  block-device bytes in host pages before any userspace code can move them, so
  any such path is the host bounce the project exists to remove.
- FIEMAP, where experts are addressed as files, is an open-time file->block-range
  translation only. It never appears in the streaming loop.

## 5. M0 feasibility gate (before any delivery code)
- Experiment 1: does the Arc GPU BAR accept inbound DMA from the NVMe controller into a large VRAM aperture? Record the result; it gates the module.
- Experiment 2: confirm the OpenCL/OpenVINO consumption path is solid. Streaming into VRAM is worthless if the kernel cannot efficiently eat what landed.
- Acceptance (red-first): a test that fails if the BAR test is not run or its result not recorded.

## 6. Engineering discipline
- Red-first always: write the failing cell first, paste raw output, then make it green.
- Measure against arcint's incumbent slot-upload path (its recorded figure is 309 us per tensor). The benchmark cell must fail the incumbent and pass the module. Do not claim a win without that cell.
- Keep diffs stated and small; the reviewer reads from a fresh clone with blob hashes verified.
- Never touch master; never push master; work on dev and mark BATCH-PENDING-REVIEW.
- No hostnames, addresses, or credentials in tracked files.
- On any close-out, record the cycle account per the move-forward rule.

## 7. Deliverables by gate
- M0: recorded experiment results plus the red-first BAR-gate cell.
- Module: the ioctl surface served, a controller DMA landing expert bytes in
  VRAM, and GPU readback that is provably breakable.
- Integration: arcint consumes the module's buffer handles; the benchmark cell
  fails the incumbent path and passes the module path, byte-exact.
