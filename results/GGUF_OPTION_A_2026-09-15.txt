######## WHAT THIS CLOSES ########
The gate was measured against a synthetic option (B) store: one file per expert,
fallocate'd, one extent each — the recommended layout and the easy case. This is
the layout the shipped artifact actually uses, and it works:

- the file->LBA translation handles extent spanning, splitting a slice into two
  requests at different dest_offsets in one buffer;
- the two halves land 280,928 sectors apart — a real physical discontinuity — and
  reassemble correctly in VRAM;
- both slices byte-match an ordinary pread of the same file range;
- via_host_bounce stays 0.

M4_API.md's own words for option (A): "an expert can span an extent boundary ->
multi-segment DMA". Measured: it does, and it is handled.

######## A REPORTING GAP, NOT A DATA GAP ########
`aw_ioc_stats.segments` read **0** after a run that demonstrably moved 3 segments.
The batch path updates `reads`, `batch_reads`, `bytes` and `max_inflight` but
never `segments`. The uAPI documents that field as making gather visible
("nonzero count means the extents were gathered"), so it is currently lying by
omission. The per-request `out_segments` IS correct — it reports real bios since
the BIO_MAX_VECS fix. Fix the aggregate counter.
