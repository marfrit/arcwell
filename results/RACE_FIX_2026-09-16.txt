==== rev 5 verification: the concurrency fix on hardware ====
date: 2026-09-16
host: the target host, kernel 7.0.14-12-pve, Arc Pro B60, fresh boot (clean BAR)

WHAT THIS CLOSES. REVIEWER_PROMPT.md section 13 and BACKLOG.md T23 shipped a
memory-safety fix that was compile-checked only: built on a different kernel and
a different architecture, never loaded, with a new cell that had never been run.
That gap is now closed. Everything below was executed.

  module srcversion   0CAA5C74C7EFBCD27125AD3   (fixed)
  supersedes          D28A49C0C00071F811D65EF   (rev 4, the pre-fix module every
                                                 other file in results/ was
                                                 measured with)

The srcversion MOVED, which is the point: rev 4's "byte-identical" pin is void
and this file is what replaces it. Every other result in this directory was taken
on the old module. The transfer paths they measured are untouched by this change
-- it is confined to batch collection and move_notify -- and the suite below
re-passes on the new module, but the numbers themselves were not re-taken.

THE CELL THAT HAD NEVER RUN. aw_wait_race_test, all three legs. The red leg
asserts the buggy contract (both collectors succeed) and goes red on the fixed
module; the loser gets -EBUSY (-16) without waiting; the collected id is -EINVAL
afterwards. No double free, no parked waiter, and dmesg has no arcwell WARN, BUG
or oops this boot.

NOT DONE, deliberately: the cell was NOT run against the PRE-FIX module. Doing so
would exercise a double kfree() and a double kref_put() in a live kernel on a host
that also runs unrelated containers, and the likely outcome is a panic. The red
legs establish that the assertions discriminate; they do not establish that this
cell would have caught the original bug on a running kernel. That distinction is
left standing rather than papered over.

A SECOND PACKAGING DEFECT, found by running the installer rather than reading it.
The version-purge loop added in T22 ran AFTER the staging step, and since the
purged set normally includes the version being installed, it deleted
/usr/src/arcwell-<ver> that had just been staged. `dkms add` then failed, and the
host was left with the module REMOVED and nothing installed -- a worse outcome
than the stranding it was written to prevent. The loop now runs first. Verified
by planting a stale arcwell/0.0.0 and watching both versions get removed and only
0.0.1 return.

That is two turns in a row where a packaging change looked right and was wrong.
Both were caught by executing it; neither would have been caught by reading it.
