PROBLEM: AW_IOC_MAP_BUFFER registered a buffer forever. M4_API.md specified
map + read + stats and no release call. There was no unmap ioctl, no .release
handler, and no per-client ownership, so every registration leaked a pinned VRAM
buffer and a dma-buf reference. Expert streaming registers continuously, so this
made the surface unusable for its own stated purpose. It also meant a stuck
client held the module: `rmmod` failed with "Module arcwell is in use" because an
interrupted test still had /dev/arcwell open.

IMPLEMENTED:
  - AW_IOC_UNMAP_BUFFER (_IOW(AW_IOC_MAGIC, 4, __u32)), documented in aw_uapi.h
    as an addition to the original contract, with the reason.
  - Per-open client context; buffers belong to the file that registered them.
  - .open / .release file operations; closing the fd reclaims everything, so a
    crashing client cannot strand VRAM.
  - kref on each buffer, so AW_IOC_UNMAP_BUFFER cannot free a buffer out from
    under an in-flight AW_IOC_READ_BLOCKS.
  - aw_ioc_stats gains buffers_live and buffers_peak. If peak only ever climbs,
    the client is leaking registrations.
