THE STRONGEST STATEMENT FIRST. The tree that ships builds a module whose
srcversion is BYTE-IDENTICAL to the one that produced every measurement in
results/:

    fresh (this tree)   : D28A49C0C00071F811D65EF
    loaded (measurement): D28A49C0C00071F811D65EF

So the removals took away files that contributed nothing to the shipped object,
which is exactly the claim being made about them.

Build, from a clean tree, against the running kernel's headers:

    $ make -C /lib/modules/$(uname -r)/build M=$(pwd) modules
    MAKE_RC=0
    arcwell.ko  aw_dma_map_probe.ko  aw_m0_gate.ko  aw_p2p_provider_probe.ko

On insmod, udev created /dev/arcwell as crw-rw---- root:render without help, so
packaging/dkms/99-arcwell.rules does what it claims.

TWO CELL DEFECTS FOUND AND FIXED WHILE RUNNING THIS

1. aw_batch_test read `max_inflight` as if it described the batch it had just
   submitted. It does not: it is a MODULE-GLOBAL HIGH-WATER MARK that is never
   reset, so an earlier, larger run leaves it high and the leg silently stops
   testing anything. It printed "note: max_inflight=193, expected 16" and passed.
   This is the same defect class as the absolute via_host_bounce assertions fixed
   earlier in the campaign, in a second place. The cell now takes a baseline and
   says which of the two readings it got. On a freshly loaded module:

       max_inflight 0 -> 16: THIS batch raised the mark to N, one bio per buffer

   On a dirty module it now declines to conclude, in as many words, instead of
   printing a number that looks like a result.

2. aw_batch_test and aw_lifecycle_test took the DRM node as a bare positional
   argument while every other cell takes --drm PATH. Passing --drm to them
   silently opened nothing and they reported "FAIL -- open drm". Both now accept
   either spelling.

results/E2E_2026-09-15.txt, results/CL_IMPORT_2026-09-15.txt and

the consumption leg was not re-executed against this exact tree, only the
